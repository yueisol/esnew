# HI, ESOL — AI Fashion Photoshoot Studio

한국어 Next.js 웹앱. 모델 참조/상품 이미지 → 구조화된 OpenAI 분석 → 카테고리별 10/11컷 촬영 계획 → 개별 Images Edits 요청 → 자동 검수 → 승인·개별 JPG/PNG·ZIP 다운로드를 구현합니다. 모킹은 `tests/mock-worker.ts`에서만 사용합니다. 운영 코드에는 가짜 결과 또는 성공 처리가 없습니다.

## 실행

Node.js 24 이상이 필요합니다.

```bash
npm ci
cp .env.example .env.local
# .env.local의 키와 스튜디오 비밀번호, 세션 비밀값 입력
npm run dev
# 별도 터미널
npm run worker
```

프로덕션: `npm run build && npm start`. start는 웹과 워커를 감독하며 워커 종료 시 웹을 유지하고 워커만 백오프로 재시작합니다. 웹 종료 또는 서비스 종료 신호에는 전체 프로세스를 정리합니다. 스튜디오 로그인 후 유이솔 모델에 설정집/얼굴/체형 이미지를 등록하고 상품 누끼컷을 올리세요. 채팅 첨부 이미지 원본은 저장소에 포함되어 있지 않으므로 직접 업로드해야 합니다.

## 환경변수

| 이름 | 용도 |
| --- | --- |
| `OPENAI_API_KEY` | 서버 전용 OpenAI 키. `.env.local` 또는 Render Secret에 입력 |
| `IMAGE_MODEL` | 기본 `gpt-image-2.6-sunburst` |
| `VISION_MODEL` | 기본 `gpt-4.1`, Responses 이미지 이해·구조화 출력 |
| `STUDIO_PASSWORD` | 비공개 스튜디오 공유 비밀번호 |
| `SESSION_SECRET` | 강한 무작위 32바이트 이상 문자열. 세션 서명에 사용 |
| `DATA_DIR` | 기본 `.data`, 운영에서는 반드시 영구 디스크 경로 |
| `GENERATION_CONCURRENCY` | 기본 1, 최대 3 |
| `COOKIE_SECURE` | HTTPS 배포에서 반드시 `true` |
| `APP_ORIGIN` | 프록시 뒤 배포 시 정확한 공개 origin (예: https://example.onrender.com) |

키는 브라우저로 전송하지 않습니다. 서버 API/이미지/다운로드 모두 서명된 HttpOnly 세션 쿠키로 보호하며 동일 스튜디오의 사용자들이 데이터를 공유합니다. 개인별 계정/테넌트 분리가 필요한 SaaS 구조는 아닙니다. 외부 이미지 공개 URL을 생성하지 않습니다. 업로드는 MIME 허용 목록, 실제 이미지 디코딩, 픽셀 수, 20MB 파일/21MB 요청 크기, 대상별 24장 제한을 검증합니다. EXIF는 정규화 과정에서 제거됩니다.

## OpenAI 연결

`https://api.openai.com` outbound HTTPS 허용 및 결제가 가능한 API 프로젝트가 필요합니다. 일부 이미지 모델은 조직 인증/모델 권한이 필요할 수 있습니다. 키 입력 후 `npm run check:openai`로 모델 접근 권한을 비용 없이 조회할 수 있습니다. 공식 SDK의 Images Edit 타입을 확인했습니다:
https://github.com/openai/openai-node/blob/master/src/resources/images.ts

요청 모델은 환경변수로 교체합니다. 기본 `high`, PNG, `1024x1536` 또는 정사각형 `1024x1024`, `n=1`을 사용합니다. 이전 1/1.5 모델에만 `input_fidelity=high`를 넣으며 2.x에서는 보내지 않습니다. 얼굴→설정집→체형→누끼→마네킹→디테일을 우선 선택하여 최대 16장을 전달하고 역할을 명시합니다. 생성 모델이 지원하지 않는 이름/파라미터는 오류로 표시합니다. 모델 접근 가능 여부는 실제 계정으로 요청해야 확정할 수 있습니다.

3:4/4:5는 현재 네이티브 세로 출력 전체를 유지한 채 중립색 여백을 넣어 지정 비율에 맞춥니다. 3:4는 1152×1536, 4:5는 1280×1600 캔버스를 사용하며 원본 픽셀을 확대하지 않습니다. 크롭으로 의류를 자르거나 단순 업스케일을 고해상도 원본으로 주장하지 않습니다. xhigh/max와 더 큰 네이티브 해상도는 계정·모델 지원을 실제 검증하지 못하여 현재 UI에서 제공하지 않습니다.

## 구조와 데이터

```text
src/app/page.tsx                한국어 스튜디오/결과/모델 편집 UI
src/app/api/[...path]/route.ts  인증, 업로드, 작업, 승인, 재생성, 다운로드
src/lib/db.ts                  SQLite 스키마, WAL, 트랜잭션
src/lib/schema.ts              상품 분석/촬영 옵션 검증, 유이솔 기본 프로필
src/lib/planner.ts             카테고리별 촬영 기획·참조 선택·프롬프트
src/lib/openai.ts              Responses/Images Edits, 지수 백오프
src/lib/worker.ts              영구 큐 소비, 개별 생성, 검수, 복구
scripts/start.mjs              웹/워커 감독
render.yaml                    영구 디스크 포함 Render Blueprint
```

- `models`: id, name, profile, prompt, created_at, updated_at.
- `assets`: owner_id, role(reference/face/body/cutout/mannequin/detail/result), 서버 파일 경로.
- `products`: 상품명, 구조화된 analysis.
- `jobs`: 선택 모델/상품, 옵션, 상태, 중복 방지 키, **생성 시작 시 모델·참조 스냅샷**.
- `shots`: 촬영 계획, 상태, 결과 이미지, 검수, 승인, 재생성 횟수.
- `history`: 이전 결과·계획·검수 보존. 현재 UI는 최신 결과만 표시.

SQLite DB 및 비공개 PNG는 모두 DATA_DIR 아래 저장합니다. 새로고침/브라우저 재접속 후 촬영 기록에서 복구됩니다. 재생성 시 다른 컷과 기존 결과 파일은 유지됩니다. 생성 완료 결과는 즉시 API와 화면에 나타납니다. 작업 상태는 실제 생성 및 검수 결과를 기준으로 표시합니다.

워커 중단 후 미완료 분석은 재실행합니다. 생성 중이던 요청은 실제 과금 여부를 알 수 없으므로 실패 상태로 전환하여 사용자가 재시도하도록 합니다. 저장 후 검수 중이던 이미지는 검수만 재개합니다. 이미지 생성의 429 응답은 최대 3회 백오프하며, 5xx·연결 끊김·시간 초과는 원격 과금 여부가 불명확하므로 자동 재전송하지 않습니다. 분석·검수는 429/일시적 서버 오류에 백오프합니다. 네트워크 타임아웃은 비용 중복 위험 때문에 자동 재전송하지 않습니다. 원격 API의 정확히 한 번 실행을 보장하지 않습니다. **동일 DATA_DIR에서 워커는 한 개만 실행**해야 합니다.

## Render

1. 이 코드를 GitHub 저장소에 커밋/푸시합니다.
2. Render에서 Blueprint로 `render.yaml`을 선택합니다.
3. OPENAI_API_KEY, STUDIO_PASSWORD를 보안 설정에 입력합니다. SESSION_SECRET은 자동 생성합니다.
4. APP_ORIGIN에 서비스의 HTTPS 주소를 설정합니다.
5. 유료 영구 디스크 `/var/data/hi-esol`이 연결되었는지 확인하고 배포합니다.

SQLite와 파일을 같은 디스크에서 사용하므로 **단일 인스턴스만 지원**합니다. Render 영구 디스크는 여러 서비스/인스턴스 사이에 공유되지 않으므로 별도 Render worker 서비스로 분리하지 않습니다. 자동 확장·서버리스 배포에는 PostgreSQL, 공유 비공개 오브젝트 스토리지 및 분산 큐로 이전해야 합니다. 디스크 백업/보관 기간과 비용 한도는 운영자가 설정해야 합니다. 배포/게시/푸시는 이 작업에서 수행하지 않았습니다.

## 검증

```bash
npm run typecheck
npm run build
npm test
npm run test:integration
npm run test:browser # 로컬 Chromium 필요; tests/browser.ts 실행 경로 조정
```

통합 검증은 별도 임시 DATA_DIR, 테스트 비밀번호, 고정된 모킹 이미지로 실행합니다. 실제 OpenAI 호출은 전혀 하지 않습니다. 로그인 보호, 파일 디코딩, 중복 클릭, 10/11컷 완료, 한 컷 재생성 격리, 승인, ZIP/JPG, 저장 상태 복구를 검사합니다. 촬영 플래너 단위 테스트는 10/11컷 분배, 하의 구도, 얼굴 참조 우선순위, 재시도 정책을 검증합니다.

실제 OpenAI API 키가 환경에 없어 실제 이미지 생성/검수 호출 및 결과 품질은 검증하지 않았습니다. 공식 문서 사이트 접근도 환경의 도메인 정책에서 차단되어 공식 GitHub SDK를 참고했습니다. 얼굴 동일성, 소재·로고·단추·거울 물리 정확도는 생성형 모델이 보장하지 않으며 자동 검수도 완전하지 않습니다. 승인 전에 원본과 대조해야 합니다. 첫 운영 검증은 작은 비용으로 한 컷을 별도 확인한 뒤 전체 촬영을 권장합니다.

## 생성이 첫 두 장에서 멈춘 것처럼 보일 때

생성과 자동 검수는 독립 큐로 처리합니다. 검수 요청은 90초 제한 후 수동 검수 대상으로 표시하며 생성 이미지는 유지합니다. 분석/검수용 전송 이미지만 최대 1600px JPEG로 줄이고, 이미지 편집 원본과 다운로드 결과는 그대로 유지합니다. 워커 상태는 화면에서 주기적으로 갱신합니다. `image_saved`, `generation_failed`, `review_failed` 로그에는 컷 ID와 처리 결과를 남깁니다.

Render에서 `DATA_DIR=/var/data/hi-esol`, 해당 경로의 영구 디스크 연결, 인스턴스 수 1, Start Command `npm start`를 확인하세요. Environment에 경로만 입력하는 것은 디스크 연결이 아닙니다. 수동으로 생성한 Web Service에는 render.yaml이 자동 적용되지 않습니다. 임시 디스크의 데이터는 재배포/재시작으로 사라질 수 있으며, 사라진 원본 파일은 코드 수정만으로 복원할 수 없습니다. 재배포 전 기존 결과를 다운로드하세요. 메모리가 작은 서비스는 `GENERATION_CONCURRENCY=1`을 권장합니다.

## 촬영 구도 구성

새 촬영은 컨셉 3컷을 사선 원거리 / 사선 중거리 / 사선 후면 원거리로 배정합니다. 원거리에서는 인물이 화면 높이의 50–65% 정도를 차지하고 실제 배경 여백이 보이도록 지시합니다. 첫 거울 셀카는 머리부터 신발까지 포함한 전신이며, 스튜디오는 정면과 90도 측면(11장 모드에서 정후면 추가)입니다. 디테일 2컷은 얼굴을 프레임 밖으로 제외하고 상품 구조 / 원단·봉제·드레이프를 각각 80–95% 크기로 담습니다. 카테고리별로 촬영 부위를 다르게 정합니다.

참조 이미지의 얼굴 구도가 결과의 구도를 결정하지 않도록 프롬프트에서 촬영 계획을 우선하고, 자동 검수에도 방향·거리·크롭 기준을 전달합니다. 측면/후면/디테일에서 얼굴이 보이지 않는 것은 의도된 구도로 처리합니다. 생성 모델이 지시를 정확히 따르는지는 실제 결과 검수가 필요합니다. 후면 사진이 있다면 상품 누끼컷에 추가해 주세요. 확인되지 않은 후면 구조는 추측하지 않도록 지시합니다.

기존 촬영의 저장된 계획·결과는 변경하지 않습니다. 단순 재생성은 기존 계획을 유지하므로 새 구성 전체를 적용하려면 업데이트 배포 후 새 촬영을 시작하세요. 실제 API 비용을 발생시키는 자동 재생성이나 기존 작업 마이그레이션은 하지 않습니다.

## 촬영 기록

`/history`의 나의 촬영 기록에서 상품별 썸네일과 상태를 확인하고 결과 열기·ZIP 다운로드를 할 수 있습니다. 기간에 따른 자동 삭제와 만료 접근 제한은 사용하지 않습니다. 기존 DB의 만료일 값도 무시하고, 이전 버전의 만료일 설정 트리거를 제거합니다. 예전 파일 삭제 대기 목록은 실행하지 않습니다.

데이터는 서버의 DATA_DIR에 보관됩니다. 재시작·재배포 후에도 결과를 유지하려면 Render 영구 디스크 연결이 필요합니다. 자동 정리가 없으므로 디스크 용량과 백업은 운영자가 관리해야 합니다. 이전 버전에서 이미 삭제되었거나 임시 디스크에서 사라진 기록·파일은 이번 변경으로 복구되지 않습니다.

## 생성 안정성과 복구

- 기본 이미지 생성 동시성은 1입니다. 2 이상으로 설정해도 각 슬롯이 독립적으로 다음 컷을 가져오므로 느린 한 컷이 전체 묶음을 막지 않습니다. 분석과 검수 큐도 별도로 처리합니다.
- `IMAGE_REQUEST_TIMEOUT_MS` 기본값은 480000(8분)이며 이미지 요청의 429 재시도에도 같은 마감 시간을 적용합니다. 요청 시간이 초과된 컷은 실패 표시 후 나머지 컷을 진행합니다. UI에 요청 경과 시간과 **실패한 컷만 재시도** 버튼이 표시됩니다. 재시도는 추가 요금이 발생할 수 있습니다.
- 생성 API 응답은 DATA_DIR/checkpoints에 먼저 원자적으로 저장합니다. 파일 저장 중 워커가 중단되면 다음 시작에서 저장된 응답으로 결과 등록을 마칩니다. 아직 응답을 저장하지 못한 요청은 과금 여부를 알 수 없어 자동 재전송하지 않고 사용자 재시도를 기다립니다. 나머지 대기 컷은 계속 실행합니다.
- 워커 종료 시 웹을 함께 종료하지 않고 2~60초 백오프로 워커를 재시작합니다. 단, Render 인스턴스 전체가 재시작되거나 메모리 한도를 초과해 종료되면 프로세스 감독만으로 막을 수 없습니다. 영구 디스크가 필요합니다.
- Sharp 이미지 캐시와 처리 병렬도를 제한하고, 편집용 참조는 원래 해상도의 무손실 WebP로 전송합니다. 원본 파일을 변경하지 않습니다. 전송 총량은 48MB로 제한합니다. ZIP은 이미지를 하나씩 처리해 스트리밍하므로 전체 ZIP과 모든 이미지를 동시에 메모리에 보관하지 않습니다.
- Render 로그의 `generation_started`, `image_saved`, `image_recovered`, `generation_failed`, `worker_memory`, `worker_exited`로 컷별 상태와 프로세스 종료 신호를 확인할 수 있습니다. 반복적인 인스턴스 재시작에는 Render Metrics의 메모리 한도·Events도 확인하세요.

검증 명령: `node --import tsx tests/stability.ts`는 저장 응답 복구, 느린 요청·잘못된 촬영 정보의 격리, 나머지 컷 진행을 모킹으로 검사합니다. `node --import tsx tests/supervisor.ts`는 Linux에서 워커를 SIGKILL한 뒤 웹 생존과 워커 재시작을 확인합니다. 실제 OpenAI 비용은 발생시키지 않습니다.

## 자연스러운 사진 표현과 미세 그레인

생성 프롬프트에 촬영 유형별 카메라 표현(로케이션 35–50mm, 스튜디오 50–85mm, 거울 셀카는 스마트폰, 디테일은 충분한 심도의 근접 촬영)과 실제 광원·그림자·피부 미세 질감·원단 표현을 명시합니다. 과도한 피부 보정, CGI 광택, HDR, 강한 배경 흐림, 샤프닝 테두리, 색조 필터를 피하고 상품 색상과 구조를 우선합니다. 자동 검수도 미세 그레인을 의도한 효과로 구분하면서 디테일을 가리는 과한 노이즈는 문제로 평가합니다.

최종 저장 단계에서 사진 영역에 매우 약한 흑백 그레인을 적용합니다. RGB에 같은 작은 증분을 사용해 색 차이를 유지하고 검정·흰색 극단값을 보호합니다. 스튜디오는 약하게, 소재 디테일 컷은 더 약하게 적용합니다. 흐림·샤프닝·색보정은 추가하지 않습니다. 비율 보정 여백에는 노이즈를 넣지 않습니다. 원본 생성 응답 체크포인트에서 매번 동일한 시드로 처리하므로 서버 복구 시 그레인이 중첩되지 않습니다. 작업용 RGBA 버퍼는 최종 출력 크기로 제한합니다.

새 촬영과 기존 컷의 재생성에 적용됩니다. 이미 저장한 결과를 자동 수정하거나 유료 생성 요청을 실행하지 않습니다. 프롬프트와 그레인은 사진의 자연스러움을 유도하는 수단이며, 얼굴·손·의류의 생성 오류 자체를 교정하거나 실제 촬영임을 보장하지 않습니다. 실제 생성 결과를 원본 상품과 함께 검수해야 합니다.

## 촬영마다 다른 자세와 구도

각 촬영은 작업 ID를 시드로 사용해 포즈·화면 내 위치·카메라 높이와 좌우 방향·표정·자동 헤어·장소 조합을 선택합니다. 각 필수 촬영 슬롯에 4~6개의 구체적인 동작 후보를 제공하고, 같은 모델의 최근 촬영 계획 최대 110개를 참고해 직전 동일 슬롯의 포즈는 제외하며 최근 덜 사용한 포즈부터 선택합니다. 단순히 이미지 ID나 배경 이름만 바꾸지 않습니다. 의자·창틀·계단이 필요한 동작은 해당 배경 조건을 함께 전달합니다. 하의·원피스의 컨셉 중거리 컷은 기장과 실루엣이 가려지지 않도록 앉는 후보를 제외합니다.

원거리 전후면 컨셉, 전신 거울 셀카, 정측면 스튜디오, 얼굴을 제외한 디테일 크롭은 그대로 유지합니다. 사용자가 지정한 헤어스타일도 유지합니다. 모델 참고 사진의 자세를 그대로 복사하지 않도록 생성 프롬프트에 명시합니다. 별도 AI 기획 API를 추가하지 않으므로 이 선택 과정에 추가 API 비용은 없습니다.

새 촬영마다 다른 조합을 선택하지만 이미 저장된 촬영 계획은 유지합니다. 개별 재생성과 장애 복구는 같은 계획을 사용합니다. 이력 없는 기존 계획도 호환되며, 새 방식의 이력이 쌓일수록 최근 사용한 포즈를 피할 수 있습니다. 실제 이미지가 지시한 동작을 따르는지는 결과 검수가 필요합니다.
